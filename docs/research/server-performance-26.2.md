# MTR / ANTE 26.2 服务端优化记录

日期：2026-09-24。目标环境：NeoForge 26.2，9950X 独占 8 个物理核心、64 GB、Windows Server 2022，最高约 80 人。

这是一轮有范围的算法和分配优化，不是 80 人容量认证。人数之外，运行列车数、编组长度、轨道连接数、同时移动/入服人数、维度数和客户端视距都会改变负载。未修改服务器 JVM 参数、线程数、协议或存档格式，也不引入 Kotlin 运行库。

## 第一批范围

| 位置 | 原开销 | 处理方式 | 不变的行为 |
| --- | --- | --- | --- |
| MTR `RailwayDataFileSaveModule` | 逐条 `ArrayList.remove(0)` 移动剩余元素；每个保留文件在待删列表中线性查找 | FIFO 使用 `ArrayDeque`；待删路径使用保序 `LinkedHashSet` | 数据写入顺序、序列化、哈希、每次删一个文件、停服完整保存、26.2 写失败保留旧文件 |
| ANTE `TrainMixin` | 自定义 `_calculateCar` 每侧重复附近玩家判断 | 该入口每车厢计算一次，在左右侧调用期间复用结果 | 未预检/旧版 MTR 入口仍有原保护；无玩家时不扫描；有玩家时即使 `doorValue == 0` 仍扫描，保留关门副作用 |
| ANTE `RailwayDataMixin` | 每 tick 丢弃位置 Map 并新建 | 轮换并清空最旧 Map，与当前 MTR 一致 | 两帧位置历史和信号占用逻辑 |

存档队列的收益限定为**队列管理**：从可能的 O(N²) 移动/查找变为预期 O(N) 总工作量；不是整个存档过程 O(N) 的耗时保证。MessagePack 编码、哈希和同步磁盘 I/O 仍然存在，哈希集合也需要额外内存。

ANTE 的实际服务端模拟入口由 `onSimulateTrain` 替换，走自己的 `_calculateCar`。因此旧稳态路径是每车厢 2 次附近检查，优化后为 1 次。当前 MTR 自己的 `calculateCar` 入口已有外层保护，旧 MTR 则没有；两者经 ANTE 时仍保留原有 fallback 检查，不承诺都变成 1 次。预检作用域用 `finally` 恢复，避免一次异常绕过后续保护。扫描方块数量本轮没有减少，不能宣称车门逻辑整体快一倍。

## 可复现检查

使用仓库版本选择入口与 JDK 25；先构建 MTR，再构建引用其产物的 ANTE。保留完整构建输出。

```powershell
# 在 MTR 仓库；JAVA_HOME 应指向 JDK 25
.\gradlew.bat build '-Version=26.2'

# 在 ANTE 仓库，使用其相同的版本选择入口
.\gradlew.bat build '-Version=26.2'
```

`checkSaveQueueCompatibility` 对编译后的 26.2 存档模块进行回归，包含队列行为与失败保旧文件检查；纯集合工作量对比不是文件系统或多人服务器压测。保存测试仅使用临时目录，不触碰玩家存档。

本轮该检查已通过，另以同一测试的 `--baseline` / `--benchmark` 模式分别执行旧/新编译类。Java 25，本地 1 次预热、3 次测量的中位数：

| 合成工作量 | 原实现 | 新实现 |
| --- | ---: | ---: |
| 10 万条 ID 经真实 writer 队列出队，lookup 返回空以排除磁盘 | ArrayList：180.423 ms | ArrayDeque：0.442 ms |
| 2 万条唯一 Path，以固定随机顺序移除 | ArrayList：2914.702 ms | LinkedHashSet：1.007 ms |

这是说明数据结构开销的简易微基准，不是 JMH 或生产机测量，也不意味着保存全流程或 MSPT 有相同比例改善。计时不作为 CI 通过阈值，默认检查只验证行为/结构；基准在显式选择时运行。

本轮最终验证结果：

- MTR 26.2 完整 `build --offline --max-workers=4` 通过（38 秒，50 个任务），含新增存档回归以及既有数据、网络、渲染和加载入口检查；Fabric/NeoForge 产物均生成。
- ANTE 26.2 完整相同构建通过（46 秒，83 个任务），含新增 `checkServerTickWorkCompatibility` 和 `checkServerTickWeaving`，以及既有发布包、GraalJS、FML 模块、Mixin 目标与轨道构造回归。
- ANTE 行为检查执行当前方法体与隔离世界替身，覆盖服务端/客户端、远近玩家、门值 0/1、MTR/PSD/Metropolis/EyeCandy、旧 MTR 调用模式、异常恢复和两帧占用历史。另一个检查实际应用 Sponge Mixin 后检查调用边界，确认 ANTE 替代模拟入口与 Map 复用生效；它不启动游戏世界。
- 原代码基线通过行为检查；目标性能结构断言在修改前失败、修改后通过。针对旧 MTR 无外层检查的回归也捕获过直接删除内部检查的不安全候选，最终实现保留 fallback。
- 两工程发布目录已更新，但未安装到游戏实例、未修改用户世界、未提交或推送。本轮没有执行 80 人实服压测；已有 Java/依赖弃用和 native-access 警告仍存在，构建通过不等于这些警告已消除。

## 下一步优先级：先采样，再决定实现

1. **附近轨道查询的空间索引。** MTR `RailwayData.simulateTrains` 和 ANTE 的替代实现都按移动玩家全扫轨道；时刻表也会扫描。候选索引必须覆盖完整长轨、弯轨、负坐标和有向连接，查询后保留原精确判定，并覆盖加载、增加、替换、删除及清理失效节点。ANTE 当前 Bezier 缓存范围并非简单端点包围盒，超大范围还需回退路径，否则可能漏同步或令索引内存暴涨。本批不更改此语义。
2. **入服同步预算与共享快照。** `PacketTrainDataGuiServer.sendAllInChunks` 仍在一次调用中编码并发送所有分片。多人同时入服值得测；改造必须保留初始快照/增量顺序、断线取消和动态对象状态。不能直接把可变铁路对象交给后台线程。
3. **车门拓扑缓存、ETA 停站索引。** 先看长编组车站扫描、`TrainServer.simulateTrain` 到站表重建在采样中的占比，再设计失效机制。门关闭、动态放拆站台、区块卸载、循环线/折返、延误和到站传感器均需回归。
4. **自动保存共用时间预算/增量脏记录。** 当前预算在各记录类型重新计时，磁盘 I/O 仍在调用线程。队列优化不解决全部保存尖峰；后续异步写盘需要不可变快照、顺序和停服刷盘协议。

已有的同 tick 对象序列化缓存、广播 payload 复用、`Train.getIndex` 二分、信号反向索引和 Siding 临时容器复用，不再重复列作本轮新增收益。

## 公开性能结论前的验证条件

- 用同一存档的独立副本、相同 JDK/模组/视距/运行列车/硬件，分别测试基线和优化构建；预热后重复采样，避免把启动和首次资源加载当稳态。
- 场景至少包含繁忙站台与长编组、玩家分散高速乘车、多人入服、自动保存窗口；80 人目标需要真正的代表性负载，不由单机合成队列测试推算。
- 记录 MSPT p50/p95/p99/max、超过 50 ms 的 tick 比例、分配率/GC 停顿、每次保存时长、入服同步时长与发送字节。先查主线程热点，不因为有 8 个物理核心就把所有池扩大为 8。
- 功能回归包含车门开/关到零、EyeCandy 站台、无玩家附近、跨站/折返/信号、多维度以及保存后重载。公开前还应在专用服务端及客户端+服务端组合实际运行。
- JDK 25 自带 JFR 可保存本地采样，不必上传世界或日志。人工确认目标进程后可用 `jcmd <PID> JFR.start name=mtr26 settings=profile duration=300s filename=<本地文件.jfr>`；profile 有测量开销，两组应使用相同设置。参见 [JDK 25 jcmd 文档](https://docs.oracle.com/en/java/javase/25/docs/specs/man/jcmd.html)。本轮没有对生产进程启动采样。

Kotlin 的性能、维护与发布兼容性结论见 [语言评估](kotlin-runtime-evaluation.md) 的 26.2 补充，而不是旧 1.21.1 的依赖版本清单。
